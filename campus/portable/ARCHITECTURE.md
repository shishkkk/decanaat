# CAMPUS — устройство прототипа

## Клиент и сервер

Интерфейс написан на React и TypeScript. Компоненты расписания, сессии, документов и посещаемости используются и в исходном приложении Next.js, и в переносимой сборке. CSS отвечает за компоновку от 360 px, нижнюю навигацию и отдельную прокрутку ленты дат. Для просмотра опубликованной версии нужен только браузер.

Переносимый комплект содержит готовый HTML с клиентом и шрифтами. Node.js 24 обслуживает его и API на этом же компьютере. Встроенная SQLite позволяет запускать демо без установки отдельного сервера базы данных. На публичном сайте обработчик запросов работает как Worker, данные сохраняются в привязанной базе D1. Публичный сайт и локальные копии имеют отдельные базы.

## Хранение и доступ

Профили, дисциплины, оценки, даты занятий, посещаемость, заявки, сообщения и вложения связаны ключами в базе. История обработки заявок хранится отдельно от текущего статуса. Реквизиты документов личного дела в профиле — демонстрационные образцы, сформированные из данных аккаунта. Готовые электронные справки выдаются через защищённый API. В локальном режиме данные сохраняются в campus.sqlite рядом с сервером. В архиве распространяются схема и начальные примеры. После первого запуска можно закрыть приложение и вернуться к своим изменениям.

Сервер проверяет пароль через bcrypt. Сессия действует до 12 часов. Браузер получает случайный токен в cookie HttpOnly, Secure и SameSite=Lax, база хранит его SHA-256-хеш. При изменениях сервер проверяет происхождение запроса и CSRF-токен. Доступ к профилю, заявке, документу и диалогу определяется по роли и владельцу в базе. У преподавателя права на свои занятия и списки посещаемости. SQL-запросы с пользовательскими значениями используют параметры. Попытки входа ограничиваются по частоте.

Два тестовых входа общие для жюри. Посетители под одним демологином видят данные этого аккаунта. Используйте вымышленные записи. Для локальной копии защиту файла обеспечивают права доступа операционной системы. Шифрование локальной базы и автоматическое резервное копирование в комплекте не настроены.

## Рост нагрузки

Для демонстрации и небольшого пилота реляционная схема и один сервер записи упрощают сопровождение. Публичные обработчики запросов используют общую базу, поэтому сессия доступна независимо от экземпляра обработчика. SQLite хранит данные в одном локальном файле и сериализует запись. При одновременном массовом выставлении оценок или посещаемости это ограничение нужно измерить.

Перед запуском в университете нужны индивидуальные учётные записи, отключение быстрого демовхода, правила хранения и удаления документов, резервные копии с проверкой восстановления и журнал доступа. Следующий шаг при росте — измерить задержки чтения и записи, добавить постраничную выдачу уведомлений и расписание по диапазону дат, затем вынести тяжёлые вложения в закрытое объектное хранилище. При упоре в конкурентную запись можно перевести серверные запросы и миграции на PostgreSQL, сохранив HTTP API клиента. Ни предельная вместимость, ни гарантированное число одновременных пользователей нагрузочными испытаниями пока не подтверждены.
